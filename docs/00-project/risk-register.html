1目的と範囲

SiteLive Twin を PoC から運用・改善まで進めるうえで、計画どおりに進まなくなる要因（リスク）と、すでに分かっている対応すべき事項（課題）を一つの台帳で管理します。

  • リスク：まだ起きていないが、起きると目的・日程・費用・品質に影響するもの。R-番号で管理します。
  • 課題：すでに分かっていて、対応が必要なもの。I-番号で管理します。主に画面設計書 11章「課題と本番に向けた検討」から引き継ぎます。

各フェーズゲート（G1〜G4、運用後は四半期ごとの G5）では、本台帳の高スコアのリスクと未完了の課題を判定材料にします。

2評価方法

影響度と発生可能性をそれぞれ3段階で評価し、掛け合わせた値をスコアとします。

段階影響度（目的・日程・費用・品質への影響）発生可能性
3（高）ゲート判定が No-Go になる、またはフェーズが1か月以上遅れる。機密情報の漏えい対策しなければ高い確率で起きる
2（中）2〜4週間の遅れ、または範囲の縮小が必要になる起きる可能性がある
1（低）フェーズ内で吸収できる起きる可能性は低い
スコア区分対応方針
6〜9高対策を計画に組み込み、週次で状況を確認する。ゲート判定で必ず報告する
3〜4中対策と担当を決め、ゲート前に見直す
1〜2低記録して監視する

状態：未着手 対応中 完了（リスクは「監視」も使う）

6更新ルール

タイミング内容担当ロール
週次スコア「高」のリスクと、対応中の課題の状況を更新する。新しく見つかったリスク・課題を追加するプロダクトオーナー
ゲート前（G1〜G4）全項目の評価を見直し、ゲート判定書に高スコアのリスクと未完了の課題を記載するプロダクトオーナー、アーキテクト
運用後（四半期ごと、G5）運用中に見つかったリスク・課題を追加し、改善計画に反映する運用担当、プロダクトオーナー
  • 完了したリスク・課題は削除せず、状態を「完了」にして残します。
  • スコアを変えたときは、変更理由を対策欄に追記します。
  • この台帳の変更も、他の文書と同じく PR とレビューを通します。
