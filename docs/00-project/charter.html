1プロジェクトの概要

プロジェクト名現場ライブツイン（英語名：SiteLive Twin）
リポジトリ名SiteLive-Twin（Mirai-Admin-Platform 配下）
システムID（案）sitelive-twin（Mirai-Platform-Infra の systems.yaml に登録予定）
ひとことで全現場の状況を一目で把握し、問題の原因を3Dで確かめ、対策の効果をその場で試算して、すぐ決めるための業務システム
判断の流れ見る → 気づく → 原因を探す → 対策を比べる → 決める
最初の題材擁壁を含む道路改良工事（A現場：県道○○線 道路改良）

詳しい背景と構想は 企画構想案（SLT-DOC-01） を参照してください。

2目的と成功基準

目的

  • 工程・現場の状況・原価をつなぎ、遅れや異常にその日のうちに気づけるようにする
  • 対策の効果を数字で比べ、根拠のある判断を早く下せるようにする
  • 判断の経緯（誰が・いつ・何を根拠に決めたか）を記録し、次の現場の計画に生かす

成功基準（MVPで測る指標）

指標現状のイメージ目標
遅延に気づくまでの時間数日（週報ベース）1営業日以内
検知から対策承認までの時間次回の会議まで3営業日以内
重機の待機率把握できていない可視化し、10%改善
週報・日報の作成時間手作業で集計50%削減
利用率—対象者の80%が週1回以上利用
工程会議での利用—毎回この画面で議論する

計測の方法とベースラインの取り方は MVP定義書（SLT-DOC-50） で定めます。

3スコープ

区分含めるもの
範囲内全社ダッシュボード、現場一覧、現場概要、ライブツイン（3D）、4D工程（計画と実績の比較）、対策シミュレーション、承認ワークフロー、重機・稼働、日報、安全・環境、原価管理（EVM）、レポート、設定、監査ログ、ユーザー・権限
範囲内（連携）CEOS（工程・原価）、ArcSphere（3Dモデル）、MCIP（案件ID・承認・証跡）、CODIP（気象）、重機テレマティクス・入退場・IoTセンサーの取り込み、Entra ID による認証
範囲外3Dモデルや図面の作成・編集（ArcSphere・Web-CAD）、工程表・原価・契約の正本管理（CEOS）、住民向けの公開（Construction-Public-Twin-Portal）、作業単位の施工安全計画（Civil-4D-AI-Planner）、勤怠・給与
SiteLive Twin が正本として持つデータは「現場ライブ状態の集約ビュー・イベント」と「対策シミュレーション案（申請）」に限ります。それ以外は他製品の正本を参照します（ADR-0001）。

4進め方（フェーズ）

各フェーズの終わりにゲート（G1〜G4）を置き、「問い」に答えられたときだけ次へ進みます。判定の基準と必要な文書は フェーズゲート定義書（SLT-DOC-03） で定めます。

フェーズ問い出口のゲート
構想取り組む価値があるか？G0 構想承認（PoC 着手）
PoC技術的に成立するか？G1 Go / No-Go
Prototype（必要に応じて）利用者が理解・操作できるか？G2
MVP最小の価値で、本当に使われるか？G3
Staging本番に近い条件で、安全・安定して運用できるか？G4 リリース判定
Release本番環境で、対象ユーザーへ正式提供する—
運用・改善計測 → 学習 → 改善 → 次リリースG5 改善レビュー（四半期ごと）

現在地

構想フェーズの終盤です。企画構想案、オフラインデモ、システムWebUIサンプル、画面設計書ができており、G0 で PoC 着手の承認を得る段階です。これらのデモは Prototype の先行成果物として、Prototype フェーズでも使います。

7ポートフォリオ上の位置付け

「みらい建設土木DX・AI統合基盤 全体構成 V3.6」とリポジトリ構成ベストプラクティス V3.6 に従います。SiteLive Twin は現時点で V3.6 の12リポジトリに含まれていないため、独立リポジトリとする理由を ADR-0001 で示し、G3 で再評価します。

技術的な判断は ADR（docs/adr/）に、リスクと課題は リスク・課題管理台帳（SLT-DOC-04） に記録します。コードの変更は main への直接 push を禁止し、PR → CI → 人のレビュー（通常2名、重要な変更は3名）を経て取り込みます。

9前提・制約

  • 他リポジトリのデータベースには直接接続しません。版付きの契約（contracts/）・API・イベントで連携します。
  • AI は MCAH の Tool Gateway・Model Gateway を経由してだけ使います。
  • 認証は Entra ID と Cloudflare Access を使い、権限はサーバー側でも必ず判定します。
  • 技術スタックは OS・アプリ選定ベストプラクティス V3.5 に従います（ADR-0002）。
  • リリースは SBOM・署名・Attestation・digest 固定で行い、latest タグは使いません。
  • PoC では、取得できないデータをダミーや手入力で代用してよいものとします。
