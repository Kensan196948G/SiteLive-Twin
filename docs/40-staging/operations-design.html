1目的と範囲

Staging と本番で SiteLive Twin を安全・安定して運用するための体制、監視、バックアップ、障害対応、定常作業を定めます。Staging フェーズの問い「本番に近い条件で、安全・安定して運用できるか？」に答えるため、本書の内容を Staging で実際に運用し、結果を G4（リリース判定）の材料にします。

本書の数値（稼働率・RPO・RTO・しきい値）は v0.1 時点の案です。MVP の実績と Staging での検証を踏まえて確定します。

対象

  • SiteLive Twin のアプリケーション（Web 画面、API、取り込み処理、配信処理）とデータベース（PostgreSQL 18）
  • Staging 環境と本番環境。PoC・MVP の環境は対象外（簡易な運用で可）
  • 連携先（ArcSphere、CEOS、MCIP、CODIP、MCAH、認証基盤）は各リポジトリの運用に従い、本書では連携部分の監視だけを扱います

6アラートと連絡経路

図1　アラートの連絡経路

  • 警告：運用担当へ通知します。業務時間内に確認し、必要なら開発へ連絡します。
  • 緊急：運用担当と開発へ同時に通知します。重大度1の場合はプロダクトオーナーにも連絡します。
  • 利用者への周知（障害のお知らせ・復旧のお知らせ）は、プロダクトオーナーの判断で運用担当が行います。

3D モデル、工程・原価、案件・承認の証跡は、それぞれ正本を持つ ArcSphere・CEOS・MCIP 側でバックアップします。SiteLive Twin では保存しません。

復旧訓練

  • Staging 期間中に1回以上、バックアップから別の環境へ復旧し、RTO 4時間以内に業務を再開できるかを確認します。
  • 訓練の結果（かかった時間、手順の不足、データの欠け）を記録し、G4 の判定材料にします。
  • 本番運用後は半年に1回、訓練を行います。

8障害対応

重大度の定義

重大度状態例初動の目標復旧の目標
1（緊急）全利用者が使えない。または情報漏えいの疑いログインできない、データベース停止、権限外のデータが見える15分以内4時間以内
2（高）主要な機能が使えない、または誤った値が表示される取り込みが止まり現場の状態が更新されない、承認ができない、EVM の値が誤っている30分以内1営業日以内
3（中）一部の機能に不具合があるが、代わりの手段があるCSV 出力ができない、一部の画面が遅い当日中次回のリリース
4（低）表示の乱れなど、業務への影響が小さい文言の誤り、レイアウトの崩れ3営業日以内計画的に修正

10リリース手順の概要

ポートフォリオ共通の統制に従います。詳しい手順は Release フェーズのリリース計画書で定めます。

  1. 変更はブランチで行い、PR を作る（main へ直接 push しない）
  2. CI で自動テスト、依存関係の検査、コンテナイメージの作成を行う
  3. 人のレビューで承認する（通常の変更は2名、重要な変更は3名）
  4. リリース成果物に SBOM・署名・Attestation を付け、イメージは digest で固定する（latest タグは使わない）
  5. Mirai-Platform-Infra の envs/stg/releases.yaml を更新して Staging に配置し、確認する
  6. 確認後に envs/prod/releases.yaml を更新して本番に配置する。問題があれば直前の digest へ戻す
