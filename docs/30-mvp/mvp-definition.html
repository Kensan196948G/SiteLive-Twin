1目的

MVPで確かめる問いは「最小の価値で、本当に使われるか？」です。実際の1現場で約3か月（2027年2月1日〜4月30日、案）運用し、利用者が日々の業務の中で使い続けるか、遅れへの気づきと判断が早くなるかをKPIで確かめます。

  • 機能は「見る → 気づく → 原因を探す → 対策を比べる → 決める」を1現場で回すのに必要な分だけに絞る
  • 効果はKPIで測り、導入前（ベースライン）と比べる
  • 使われなかった場合は、その理由を記録して次の判断材料にする

5KPI計測計画

ベースラインはMVP開始前の4週間（2027年1月、案）に、現在のやり方（週報・工程会議・Excel）で取得します。計測に必要な時刻は、FR-170の計測ログで自動的に記録します。

KPI定義計測方法ベースラインの取り方目標値計測頻度
遅延検知リードタイム工種の遅れが発生（計画比で1日以上）してから、関係者が気づくまでの時間遅れの発生時刻（実績データから判定）と、通知の既読・画面の確認時刻の差直近の工事の週報・会議録から、遅れが最初に報告されるまでの日数を調べる数日 → 1営業日以内週次
対策決定までの時間遅れの検知から、対策が承認されるまでの時間計測ログ（検知・起案・承認の時刻）会議録から、対策を決めるまでの日数を調べる3営業日以内案件ごと
重機待機率重機の稼働時間のうち、待機（エンジンはかかっているが作業していない）の割合テレマティクスの稼働・待機・停止の時間MVP開始後の最初の2週間を基準にする（それ以前は計測手段がない）可視化し、基準から10%改善週次
週報・日報の作成時間週報・日報1件の作成にかかる時間利用者への記録票（開始・終了時刻）、画面の操作時間導入前に同じ記録票で2週間計測50%削減月次
利用率対象の利用者のうち、週1回以上ログインして画面を確認した人の割合ログイン・画面表示の記録—（新規）80%以上（毎週）週次
工程会議での利用工程会議でこの画面を使って議論した回数の割合会議の記録（現場所長が記入）—（新規）毎回（100%）会議ごと

KPIの値は月次でプロダクトオーナーが集計し、経営層に報告します。目標に届かない場合は、理由を利用者に聞き取って記録します（使われない理由はMVPの重要な結果です）。

6運用ルール

  1. 工程会議ではこの画面を使う。資料は事前に作らず、現場概要・4D工程・対策シミュレーションを画面に映して議論する。
  2. 現場所長は毎朝、現場概要と通知を確認する（目安5分）。
  3. 遅れの通知が出たら、当日中に原因を確認し、必要なら対策を起案する。
  4. 対策の承認は、起案者以外の経営層が行う。承認の判断は3営業日以内を目安にする。
  5. 日報は自動作成された内容を確認・追記して、当日中に提出する。
  6. データが欠測している場合は、画面の「データなし」の表示を信じ、推測で補わない。気づいたらシステム管理者に連絡する。
  7. MVP期間中は従来の週報も並行して作成し、KPIの比較に使う（最初の4週間のみ）。

7サポート体制

内容窓口対応時間の目安
操作の質問、表示の誤りシステム管理者（DX推進部）平日 当日中に回答
画面が開かない、データが更新されないシステム管理者 → 開発平日 4時間以内に一次回答
改善の要望プロダクトオーナー隔週の振り返りで扱う
情報漏えいの疑い、不正なアクセス情報セキュリティ担当直ちに連絡

運用開始の週に、現場で30分の説明会を行います。隔週で利用者との振り返り（30分）を行い、要望と使われない理由を集めます。

9G3判定基準

判定条件その後
Go（Stagingへ）6つのKPIのうち、遅延検知リードタイム・対策決定までの時間・利用率を含む4つ以上で目標を達成。利用者の継続利用の意向がある。重大な障害・情報漏えいが0件Stagingで本番に近い条件の検証へ進む
条件付きGo目標達成が3つで、未達の理由と改善策が明確。利用率は60%以上改善策をStagingの期間中に入れ、運用・改善の最初のG5で再確認する
No-Go利用率が60%未満、または目標達成が2つ以下使われなかった理由をもとに範囲を見直し、MVPを延長または中止する

判定はプロダクトオーナーが起案し、経営層が承認します。テストの合否はテスト計画書（SLT-DOC-51）、フェーズ全体の考え方はフェーズゲート定義書（SLT-DOC-03）を参照してください。
