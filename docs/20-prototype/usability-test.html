1目的と実施要否

Prototypeで確かめる問いは「利用者が理解・操作できるか？」です。実際の利用者に操作してもらい、迷う場所・誤解する表示・足りない情報を、MVPの開発前に見つけます。予定期間は2027年1月5日〜1月29日（4週間、案）です。

このフェーズは必要に応じて実施します。G1の判定時に、次の基準で実施するかを決めます。

判断基準
実施する次のいずれかに当てはまる：PoCで画面の構成や操作の流れを大きく変えた／新しい画面（3Dの部材と工程の紐付けなど）を追加した／パイロット現場の利用者がまだ画面を見ていない
省略するシステムWebUIサンプルの画面構成から大きな変更がなく、利用者代表がデモで操作を確認済み。この場合は、MVPの最初の2週間で同じタスクを使った簡易評価を行う

2対象プロトタイプ

対象置き場所評価に使う範囲
システムWebUIサンプル（15画面、ロール別権限、承認ワークフロー、監査ログ）prototypes/system-webui/主な評価対象。全タスク
オフラインデモ（5ステップ）prototypes/offline-demo/sitelive-offline-demo.html説明用。評価前の導入として見せる
PoCで作った画面（3D表示、リアルタイム更新）src/PoCで追加・変更した画面がある場合のみ

画面の仕様は画面設計書（SLT-DOC-20）を参照します。サンプルのデータはすべて架空です。

5成功基準

指標基準測り方
タスク完了率各タスク80%以上（手助けなしで完了）完了・手助けありで完了・未完了の3段階で記録
所要時間参加者の中央値が目標時間以内指示を読み終えてから完了までをストップウォッチで計測
SUS（システムユーザビリティ尺度）平均70点以上全タスク終了後に10問のアンケート
重大な問題0件（誤った判断につながる表示、データを失う操作）観察記録から抽出

6進め方

  1. 参加者1人につき約60分。進行役と記録役の2人で行う（対面またはオンライン）。
  2. 最初の5分でオフラインデモを使って製品の目的だけを説明する。操作方法は説明しない。
  3. タスクを1つずつ渡し、考えていることを声に出しながら操作してもらう（思考発話法）。
  4. 参加者が3分以上止まった場合のみ、ヒントを1回出す（「手助けあり」として記録）。
  5. 全タスクの後にSUSのアンケートと、5分間の自由な感想を聞く。
  6. 画面の録画は参加者の同意を得た場合のみ行い、評価が終わったら削除する。

9改善の反映

  1. 見つかった問題を重大度順に並べ、画面ごとに改善案を作る。
  2. 重大な問題はMVPの開発前に必ず直し、同じタスクで再確認する（参加者2名以上）。
  3. 中・軽微の問題は、MVPの課題一覧に登録して優先度を決める。
  4. 画面の変更は画面設計書（SLT-DOC-20）に反映し、版を上げる。
  5. 要件に影響する場合は要件定義書（SLT-DOC-10）も更新する。

10G2判定基準

判定条件
MVPへ進む全タスクの完了率80%以上、SUS平均70点以上、重大な問題が0件（修正後の再確認で解消を含む）
条件付きで進む完了率80%未満のタスクが1つ以内で、改善案がMVPの最初の4週間で入れられる
見直し完了率80%未満のタスクが2つ以上、またはSUSが60点未満。画面構成を見直して再評価する

G2の承認者はプロダクトオーナーです。判定の結果は経営層に報告します。フェーズ全体の考え方はフェーズゲート定義書（SLT-DOC-03）を参照してください。
