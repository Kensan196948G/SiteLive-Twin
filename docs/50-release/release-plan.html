1目的と範囲

Release フェーズの問いは「本番環境で、対象ユーザーへ正式提供する」です。本書は、G4（リリース判定）を通過したあと、本番環境に安全に切り替え、対象ユーザーが使い始められるようにするための計画を定めます。

範囲に含めるもの

  • 本番環境へのデプロイと、Mirai-Platform-Infra の envs/prod/releases.yaml への登録
  • MVP 現場のデータ・設定・申請履歴の本番への移行
  • 対象現場への段階的な展開（ウェーブ）
  • ロール別の利用者教育と、問い合わせ窓口の立ち上げ
  • リリース後2週間のハイパーケア（重点監視）

範囲に含めないもの

  • MVP で対象外とした機能（多段承認、他支店向けの設定など）。運用・改善計画のバックログで扱います。
  • 3D モデル（ArcSphere）、工程・原価（CEOS）、承認・証跡（MCIP）のデータ本体。SiteLive Twin は参照のみです。
前提：リリース判定書（G4）で「Go」と判定され、運用設計書の運用体制が整っていること。

3リリース手順

ポートフォリオ共通のリリース統制に従います。main への直接の push は行いません。

手順作業担当確認すること
1ブランチで変更し、プルリクエスト（PR）を作成開発PR 本文に変更内容・テスト結果・影響範囲・残課題を書く
2CI（自動テスト、静的解析、依存関係の脆弱性検査）CIすべての必須チェックが成功している
3Human Review（通常変更は2名、重要変更は3名の承認）アーキテクト、情報セキュリティ担当承認者に起案者本人を含めない
4main へマージし、リリースタグ（例：v1.0.0）を付ける開発CHANGELOG を更新している
5コンテナイメージのビルド、SBOM の生成、署名、Attestation の付与CI署名と Attestation を検証できる
6イメージを digest で固定して本番へデプロイ運用担当latest タグは使わない
7Mirai-Platform-Infra の envs/prod/releases.yaml を更新（PR 経由）運用担当登録した digest と稼働中のイメージが一致する
8本番での確認（ログイン、主要画面、CEOS・ArcSphere・MCIP との連携、承認の記録）運用担当、プロダクトオーナー本番確認チェックリストがすべて合格
  • 本番 URL：（未定：本番 URL）。検証環境は sitelive-stg.mirai-dx-platform.com（案）です。
  • 認証は Entra ID と Cloudflare Access を通します。リリース前に対象ユーザーのアクセス権を付与しておきます。
  • リリース作業は、現場の作業がない時間帯（平日 18時以降）に行います。

4データ移行

MVP 現場で作られたデータのうち、SiteLive Twin が正本を持つものだけを移行します。参照データ（3D・工程・原価・承認記録）は各正本システムから取り直します。

データ扱い方法確認
現場ライブ状態のスナップショット・イベント移行するMVP 環境のデータベースから抽出し、本番へ取り込む件数と期間が一致すること
対策シミュレーション案（申請）と履歴移行する申請番号を引き継ぐ。承認・差戻しの記録は MCIP の記録と照合する申請番号・状態・履歴の件数が一致すること
日報移行する提出済みの日報を移行する。下書きは移行しない日付ごとの件数が一致すること
設定（しきい値・通知）移行するMVP で調整した値を本番の初期値にする設定画面で値を目視確認
監査ログ保管するMVP 期間分はアーカイブとして保管し、本番では新しく記録を始めるアーカイブを読み出せること
3D モデル・工程・原価・承認記録移行しないArcSphere・CEOS・MCIP を参照する本番で参照できること
テスト用のデータ・アカウント移行しない本番には持ち込まない本番にテスト用アカウントがないこと

移行のリハーサルは Staging 環境で1回以上行い、所要時間を測っておきます。

5切り戻し計画

切り戻しを判断する基準

  • ログインできない、または主要画面（全社ダッシュボード・現場概要・承認ワークフロー）が使えない状態が30分以上続く
  • 承認の記録が MCIP に残らない、または権限の判定が誤っている（他人の申請を承認できるなど）
  • 移行したデータの件数・内容に不一致があり、当日中に直せない
  • 情報セキュリティ担当がセキュリティ上の問題と判断した

判断はプロダクトオーナーが行い、運用担当が実施します。判断がつかないときは切り戻しを優先します。

手順

  1. envs/prod/releases.yaml を直前のリリースの digest に戻す PR を作成し、承認を得て反映する
  2. データベースはリリース直前に取得したバックアップから復元する（リリース後に作られたデータは控えを取ってから戻す）
  3. 主要画面と連携の動作を確認する
  4. 利用者へ切り戻しを告知し、原因と再リリースの予定を共有する

切り戻しの目標時間：判断から60分以内。Staging で一度リハーサルを行います。

6利用者教育

教材は利用者マニュアル（ロール別）を使います。研修はロールごとに60分程度で行い、実際の現場データで操作します。

対象時間内容実施時期
経営層（支店長・工事部長）60分全社ダッシュボードの見方、アラートから現場概要への移動、承認ワークフロー（承認・差戻し、自分の起案は承認できないこと）各ウェーブの開始前
現場所長・工務60分現場概要・ライブツイン・4D工程で原因を探す流れ、対策シミュレーションと起案、日報の作成、通知と検索各ウェーブの開始前
システム管理者60分設定（しきい値・通知）、監査ログの確認、利用者の追加とアクセス権、障害時の連絡W1 の開始前
全員（工程会議）30分工程会議でこの画面を使う進め方（全社ダッシュボード → 現場概要 → 4D工程 → 対策シミュレーション）各現場の最初の工程会議
  • 研修後に簡単な理解度チェック（5問）を行い、つまずいた操作をマニュアルの改訂に反映します。
  • 研修の録画と資料は社内の文書管理（CDE）に置きます。

9リリース後の初期監視（ハイパーケア）

各ウェーブの開始から2週間をハイパーケア期間とし、通常より手厚く監視・支援します。

  • 運用担当と開発が毎朝15分の確認会を行い、障害・問い合わせ・利用状況を確認します。
  • 監視する項目：応答時間、エラー率、連携（CEOS・ArcSphere・MCIP・重機データ）の遅れ、ログイン失敗、データ更新の遅れ（5分以内）
  • 利用状況：日ごとのログイン人数、起案数、承認までの時間、日報の提出数
  • 重要度1・2の障害は、修正を緊急リリースとして扱います（手順は3章と同じ。承認は重要変更として3名）。
  • ハイパーケア終了時に、運用・改善計画の通常の運用へ引き継ぎます。
